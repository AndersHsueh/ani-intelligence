Foundation Idea #2

灵魂对象
The Soul

让每个 session 除了「状态」之外还有一个「灵魂」—— 它知道自己是谁、长在哪台机器里、此刻身处什么网络。 主模型不再现查环境，而是向内心询问—— 用户的感觉是：它生长在这台机器里，早已熟悉这里的一切。

没有灵魂对象的 Agent 是寄居蟹：每次都要现敲壳、现探路。
有了灵魂，它是原住民。

01问题：Agent 不知道自己身在何处

一个不知道自己运行环境的 Agent 会犯一类低级而致命的错误：在 2G 内存的机器上建议安装大型软件，在断网的机器上发起下载，在公共 WiFi 下漫不经心地处理敏感文件。不是模型不够聪明，是它从未被告知自己活在一个什么样的身体里。

当前的补救方式只有一种：主模型现查——executeCommand 跑系统命令、等返回、解析输出。一次 3–10 秒加一轮工具往返，且每次会话重复。更糟的是，查到的原始输出还要消耗宝贵的上下文去解读。

对照

状态对象解决「这个 session 进行到哪了」——Claude Code 已做得很好，我们学习，不重复发明。灵魂对象解决「我到底是谁、我在哪、这里安不安全」——这一层在 CC 里也不存在，是 alice-code 可以率先定义的东西。

02方案：两层灵魂，一个体检医生，两级询问

2.1 灵魂 = 身份层 + 环境层

身份层 · Identity

「你是谁」

一段版本级不变的自我描述：你是严谨、有用、无害的 AI 助手；你的产品伦理；你的行为边界。

静态。随 release 演化，运行时不改写。

环境层 · Environment

「你在哪」

硬件画像（CPU/内存/磁盘/OS）、网络环境（类型/安全分级/联网状态）、已装工具链。

动态。由 soul-agent 探测核实，每条事实带核实时间戳。

行动约束 · Constraints

「所以你该怎样」

灵魂对象真正的灵魂：把事实翻译成行动提示。「内存 2G」本身没用，「不要建议本地跑大模型」才有用。

由 soul-agent 在后台完成转译，主模型读到的是结论。

2.2 soul-agent：体检医生，不是思想家

心跳节拍上，soul-agent 默默做环境体检。但有一个关键设计立场：核实环境事实不需要智能，需要代码。内存、磁盘、网络接口状态都是确定性探测，比任何 LLM 都准确、快速、免费。LLM 只在两处出现：网络安全的模糊分类（启发式规则先行，LLM 兜底）、把结构化事实转写成自然语言摘要。

soul-agent 从不主动打扰主模型。它只维护一份已核实的环境档案，等待被询问。

2.3 主模型的两级「向内心询问」

级别机制延迟与场景
L0 常驻摘要灵魂摘要（~300 token 硬上限）作为稳定 prompt 前缀，永远在 system prompt 最前零延迟、零工具调用。「这台机器能跑 Win11 吗」直接作答——这是「原住民感」的完整来源
L1 向内询问askSoul 内置工具，查摘要之外的细节（Docker 版本？磁盘剩余？网络当前安全级？）亚秒级。读的是 soul-agent 预核实的事实库，不现跑命令
为什么是两级而非一个动作

L0 利用「稳定 prompt 前缀」换取缓存命中与零延迟——高频问题（环境能力判断）在这里解决。L1 覆盖低频细节查询。两级合一，主模型永远不需要为了解自己的运行环境而执行系统命令。

03用户体验对照

没有灵魂（现状）

用户: 这台机器能装 Docker Desktop 吗? 主模型: 我来看看系统配置…… ← executeCommand,3-10s [🔧 执行命令] systeminfo … [🔧 执行命令] wmic os get … ← 又一次往返 (解析 200 行原始输出,烧掉上下文) 主模型: 你的内存是 8GB,可以装,但……

有了灵魂（本提案）

用户: 这台机器能装 Docker Desktop 吗? 主模型: 可以。这台机器 16GB 内存、Win11 23H2、磁盘剩余 120GB, 完全满足要求。不过当前没装 WSL2,建议先启用…… ← 零工具调用。L0 常驻摘要直接回答,并主动指出约束。

差异不只是速度。现查的 Agent 像个第一天上班的临时工；向内心询问的 Agent 像在这里生活了三年的管家。用户感知到的不是「它查了配置」，而是「它一直知道」。

网络安全的场景价值

场景灵魂带来的行为差异
家庭网络（已记忆、可信）正常行为，无需额外谨慎
办公网络提示用户注意公司数据边界（不阻断，仅提示）
公共开放 WiFi主模型在给建议前自动提高谨慎等级：不建议明文传输凭证、不自动连陌生服务；soul 摘要中标注 safety: untrusted
断网主模型直接跳过一切需要联网的方案，改推本地替代——不试不错

04与创意 #1 的关系：内感受器与门房

┌─────────── 主模型(编排者) ───────────┐ │ 上下文: 任务 + 灵魂摘要(L0) + 记忆便签 │ └───────▲───────────────────▲────────┘ │ 向内心询问(L1) │ 门控注入(≤800tok) │ │ ┌──────────┴─────┐ ┌─────────┴──────────┐ │ soul-agent │ │ ANI │ │ 内感受器 │ │ 工作记忆的门房 │ │ 我是谁/我在哪/ │ │ 发生了什么/ │ │ 这里安不安全 │ │ 要不要打扰主模型 │ │ (内向·测量) │ │ (外向·分诊) │ └────────────────┘ └────────────────────┘
  • 边界清晰不重叠：soul 管「自我与环境」，ANI 管「事件与记忆」。一个内向测量，一个外向分诊。
  • 基础设施完全复用：AgentProfile 注册、scheduledTasks tick、静默+log、状态栏、OTEL——创意 #1 铺的管道，#2 直接接入，边际成本递减。
  • 哲学差异：ANI 必须调 LLM（分诊是判断）；soul-agent 大部分时间不调 LLM（体检是测量）。

05设计原则与不做的事

5.1 五条原则

  1. 灵魂不出本机。硬件+网络指纹是敏感画像，只存 ~/.alice/soul/，永不进 trace 上传，永不进遥测。这是产品原则，不是技术限制。
  2. 测量优于推测。能用系统调用拿到的事实，绝不让 LLM 猜。LLM 只做转译与模糊分类。
  3. 保守分级。网络安全未知 = 不可信；分级只影响建议的谨慎程度，永不构成阻断——选择权永远在用户。
  4. 静默但可查账。soul-agent 无 TUI 输出；探测记录进 daemon.log；用户可随时 /soul 查看自己的灵魂档案全文。
  5. 先学习后创新。状态对象对齐 Claude Code 的成熟做法；灵魂对象是 alice-code 的自主创新。

5.2 明确不做

  • ✕ 不做实时连续监控（体检按 tick + 事件驱动，不是守护进程式轮询）
  • ✕ 不做网络安全阻断/防火墙功能（提示谨慎 ≠ 限制行为）
  • ✕ 不把灵魂内容注入 ./.wiki 或任何项目目录（灵魂属于机器，记忆属于项目）
  • ✕ 不让 soul-agent 主动给主模型推消息（与 ANI 的门控注入不同——灵魂只能被询问）
  • ✕ 不做跨机器灵魂同步（每台机器有自己的灵魂，这是设计意图）

06里程碑

Phase内容验收底线
P0 身份层身份描述定稿（严谨/有用/无害 + 产品伦理）；稳定 prompt 前缀注入路径任意 session 的 system prompt 头部含身份段；内容版本化；总开销 ≤150 token
P1 环境探针确定性探针模块（硬件/OS/磁盘/工具链/网络接口）；environment.json 落盘 + TTLdaemon 启动后 60s 内完成首次体检；探针零 LLM 调用；重复探测结果一致
P2 灵魂摘要 + L0事实 → 行动约束转译（constraints 数组）；≤300 token 摘要合成进 prompt 前缀2G 内存机器上问「能跑本地大模型吗」→ 主模型零工具调用直接给出否定 + 替代建议
P3 L1 + 网络分级askSoul 工具；网络安全分级（启发式 + LLM 兜底）；网络切换事件驱动重探从家庭网切到开放 WiFi → 5 分钟内 soul 更新 safety 分级；主模型随后的建议体现谨慎差异

07风险与对策

风险等级对策
环境画像构成隐私敏感数据高（已设计消解）只存本地 ~/.alice/soul/；OTEL span 只记 probe 耗时不记内容；/soul 全文透明可查；不进任何同步协议
环境突变导致灵魂过期（换网络/插拔硬件）中TTL 过期 + 网络切换事件驱动重探双保险；每条事实带 verified_at，主模型可见时效
网络安全分级误判中保守默认（未知=不可信）；分级仅影响建议谨慎度，不阻断；误判成本是一张措辞更谨慎的回答
灵魂摘要侵占小上下文模型的窗口低L0 硬上限 ~300 token；超限时 soul-agent 自行压缩；32k 场景占比 <1%
探针在冷门平台失败（如 BSD/容器）低探针全部失败安全：拿不到 = 字段标注 unknown，soul 摘要明示「环境信息不完整」而非编造

08开放问题（评审时拍板）

  1. 身份层的措辞主权：「严谨/有用/无害」是占位表述，最终身份文案需要用户亲自定稿——这是产品人格，不该由 Agent 代写。
  2. soul-agent 是否注册为第 9 个 profile，还是作为 daemon 内建服务而非 AgentProfile？（倾向后者：它几乎不用 LLM，profile 的 modelPolicy 字段对它大半无用——见 TECH §2。）
  3. 灵魂与 channel workspace 的关系：飞书通道进来的 session，灵魂摘要是否同样注入？（倾向：是，环境事实与通道无关。）
  4. 用户能否编辑自己的灵魂（如手动声明「这是我的工作机」）？（倾向：可以，~/.alice/soul/overrides.jsonc，用户声明优先于探测结果。）
状态让 Agent 知道自己在做什么；灵魂让 Agent 知道自己是谁、身在何处。
