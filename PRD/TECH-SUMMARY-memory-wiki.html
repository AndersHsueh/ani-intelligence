Foundation Idea #1 · Engineering

工作记忆层
接线图与合同

本文档回答一个问题：这套系统接在现有代码的哪几根线上。 结论先行——五个既有模块（AgentProfile / scheduledTasks / karpathy-wiki-ingest / extractMemories / multi_model_routing） already 提供了全部挂点； 新增代码集中在三个点目录的约定层与一个分诊状态机，不发明新子系统。

01运行时架构

┌──────────── 用户项目目录 ────────────┐ │ ./.raw ./.wiki ./.outputs │ │ (append-only) (主题页) (交付物) │ └───┬───────────▲─────────────────────┘ │ append │ read(≤水位线) / write ┌────────────┐ │ │ │ 用户 TUI │ │ │ │ (alice TUI)│ │ │ └─────┬──────┘ │ │ │ chatStream │ │ ▼ │ │ ┌───────────────┐ slice │ ┌──────┴────────┐ │ agentLoop │─────────┘ │ KARPATHY │ │ (主模型 K3) │ │ ingest 执行器 │ │ │◄── 便签注入 ──│ (本地 4B) │ └───────┬───────┘ (≤800tok, └──────▲────────┘ │ 下一轮边界) │ ingest_now │ │ ┌───────┴──────────────────────────────┴────────┐ │ VERONICA daemon │ │ ┌──────────────────────────────────────────┐ │ │ │ ANI 分诊器(高速模型) │ │ │ │ tick → 脏检查 → { idle │ ingest_now │ inject } │ │ │ └──────────────────────────────────────────┘ │ │ scheduledTasks · daemon.log · OTEL spans │ └────────────────────────────────────────────────┘

三条铁律贯穿全图：

  1. ./.raw 只能 append。主会话切片只追加，KARPATHY 只读水位线之前的部分——物理上不存在写竞争，不需要锁。
  2. 主上下文只有一个人口。记忆进入主对话只有一种形态：ANI 写的注入便签，在下一个用户输入边界被 agentLoop 消费。没有第二条路。
  3. 后台全静默，日志全保留。ANI / KARPATHY 不向 TUI 吐任何实时输出；一切进 daemon.log 结构化日志 + OTEL span，状态栏暴露单行聚合状态。

03数据合同

3.1 目录与文件布局

./.raw/ # append-only 原料仓 ├── 2026-08-17/ │ ├── 0517-a3f2.md # HHMM-短hash.md,单片段一文件,写后不可变 │ └── 0522-b81c.md ├── .watermark.json # KARPATHY 消费进度(唯一的可变文件) └── .index.jsonl # 每片一行元数据,append-only ./.wiki/ # KARPATHY 编译产物,Karpathy 四件套结构 ├── INDEX.md ├── log.md # append-only └── <主题页>.md # 摘要 + 日期戳 + 互链 + 来源 ./.outputs/ # 交付物暂存(本提案不新增行为,仅归位) ./.wiki/.health.json # 状态栏数据源:lastIngestAt / pageCount / consecutiveFailures

3.2 .raw 切片格式

---
kind: decision | code | convention | manual   # manual = /raw 打点
sessionId: "..."
at: "2026-08-17T05:42:11+08:00"
tags: ["permissions", "v3.2"]
---
# 正文:切下来的原文片段,不改写、不总结——改写是 ingest 的职责

设计要点：切片层不做智能。规则匹配到什么就存什么，保真不保优；质量把控后置到 ingest（KARPATHY 二次过滤）与 lint。这让切片器可以是几十行确定性代码，零 LLM 成本，零误判面。

3.3 水位线 .watermark.json

{
  "consumedThrough": "2026-08-17/0522-b81c.md",   # 字典序即时间序
  "consumedAt": "2026-08-17T05:30:00+08:00",
  "runId": "ing-2026-0817-0530"
}

水位线是唯一的并发协调原语：KARPATHY 启动时读水位线 → 只处理其后的新文件 → 全部落盘成功后原子推进水位线（写临时文件 + rename）。崩溃恢复 = 下次从旧水位线重来，ingest 幂等因此天然成立。

3.4 注入便签 ./.wiki/.inbox/<id>.md

---
kind: memory-note
relevance: "用户当前任务与 08-14 的权限模型决策直接相关"
tokens: 612            # 写入前估算,超 800 则 ANI 自行压缩或弃写
expiresAfter: "1-turn"   # 消费一次即删除;注入率审计的依据
---
# 正文:主题页【摘要段】的摘录,非整页;末尾固定标注
# [来自 .wiki 的工作记忆 · 二等公民证据,可质疑可忽略]

3.5 健康文件 .health.json（状态栏唯一数据源）

{ "pageCount": 12, "lastIngestAt": "...", "consecutiveFailures": 0, "pendingNotes": 1 }

04ANI：分诊状态机

4.1 tick 不是心跳

daemon 心跳 5s 是活性信号，ANI tick 默认 15 分钟（daemon_settings.jsonc: scheduledTasks.aniIntervalMs）。每次 tick 的第一件事是零成本脏检查：对比 ./.raw/.index.jsonl 的行数与 mtime，无变化 → 直接 idle，全程零 LLM 调用。这是「接近零成本」承诺的技术兑现点。

4.2 三动作分诊

┌─────────────────────────┐ tick ───► │ 脏检查(行数/mtime,纯 IO) │ └───────────┬─────────────┘ │ dirty ▼ ┌───────────────────┐ │ ANI LLM 调用 │ 输入: 新增切片的 kind/tags/首行 │ (高速模型, <2k ctx)│ + .health.json + 主会话最近主题 └─────────┬─────────┘ ▼ 输出严格三选一(JSON Schema 约束, Zod 校验) ┌───────────────┼──────────────────┐ ▼ ▼ ▼ idle ingest_now inject 登 log 即可 唤起 KARPATHY 写 .inbox 便签 跑增量 ingest (可与 ingest_now 组合)

4.3 防抖动与降级

  • ingest 防抖：连续 ingest_now 合并为一次；两次 ingest 最小间隔 10min，避免用户在密集讨论时本地 4B 被反复唤醒；
  • 失败计数：KARPATHY 连续失败 → consecutiveFailures 递增 → ≥3 次状态栏显 ⚠，ANI 停止唤起（指数退避 15→30→60min），但绝不向 TUI 弹任何东西；
  • 模型缺席：本地 ollama 不可达 → 视为失败计数的一种，log 记录 karpathy.unreachable，不谎报、不fallback到主模型（那是偷用户的钱）。

4.4 ANI 的权限边界

硬约束

ANI 与 KARPATHY 的 allowedTools 白名单仅含：readFile（限 ./.raw、./.wiki、./.outputs 与项目只读）/ writeFile（限三个点目录内）/ getCurrentDateTime。无 executeCommand，无 editFile（用户工作区），无网络工具。这是 AgentProfile.allowedTools 字段的第一个强消费场景，由 permissionGate（v3.1.0 #7）强制，不靠 prompt 自觉。

05注入路径：便签如何进入主上下文

ANI 写便签 → ./.wiki/.inbox/note-xxx.md │ │ agentLoop 在每个用户输入边界(turn start) ▼ ┌───────────────────────────┐ │ 1. 读 .inbox/(FIFO, 全量) │ │ 2. tokens 校验 ≤800 │ │ 3. 拼到 system prompt 尾部 │ │ 独立小节 + 来源标注 │ │ 4. 删除已消费便签 │ │ 5. 记 memory.inject span │ │ + TUI 灰色一行提示 │ └───────────────────────────┘
  • 为什么是输入边界而不是流式中途：stream 进行中注入会破坏 LLM 的注意力连续性；输入边界是天然的上下文重组点，也是 ChatStreamEvent 已有的切分点；
  • 800 token 硬上限在两层强制执行：ANI 写前估算（超则压缩或弃写）+ agentLoop 消费前复核（超则截断并记 memory.inject.truncated）；
  • 注入率审计：便签带 expiresAfter: 1-turn，消费即删；inject 次数 / 用户 turn 数 即注入率，P3 验收 <20% 的数据来源；
  • 与 SessionMemory 的关系：全局记忆（~/.alice/memories/，跨项目）继续走既有 top-k 路径不变；./.wiki 便签是项目级记忆通道。两层并存，注入处合并去重。

09有意留白（本周期明确不做）

  • 向量索引 / embedding 检索 —— 四件套摘要 + TF 排序在 32k 场景够用；向量层等真实召回率数据说话再议；
  • LLM 自动抽取切片 —— P1 只做规则切片；自动抽取等观察期积累误判数据后单独评审；
  • 跨项目记忆合并 —— 项目间知识复用走用户手动或 TeamMemorySync，ANI 不做跨项目扫描；
  • ./.wiki 的远端同步 —— 记忆不出本机，这是产品原则不是技术限制；
  • ANI 主动发起用户对话 —— ANI 只能递便签，永远不能在 TUI 里开口说话。
一句话总结

切片器不智能、门房不越权、书记员不贵、主模型不被打扰、用户不被通知但永远可以查账——这就是工作记忆层的全部工程学。
