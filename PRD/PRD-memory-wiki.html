Foundation Idea #1

工作记忆层
Memory Wiki

让对接任意小上下文开源模型的 alice-code，拥有项目级的、自动生长的长期记忆—— 用户什么都不用做，知识库在 ./.wiki 里自己长出来； 一个静默的中断代理 ANI 决定什么时候、把哪一小段记忆，递给主模型。

上下文窗口是租来的，工作记忆是自己的。
本提案为 alice-code 增加一层项目级工作记忆：对话中有意义的片段被自动切片归档， 由常驻代理在后台编译成结构化知识库，并在——且仅在——必要时注入主对话。

01问题：32k 的房间里做不成大项目

alice-code 的产品承诺是对接不可预知的开源模型组合。这带来一个结构性约束：用户本地跑得起、跑得快的模型，上下文往往只有 32k 甚至更小。而真实的大型任务——重构一个仓库、写一份产品文档、维护一个跨周的项目——所需的工作记忆远超这个窗口。

当前系统里，会话结束即失忆。用户第二天回来，要重新解释项目背景、重新粘贴约定、重新讲一遍三天前已经讨论清楚的决策。模型没有变笨，是记忆没有留下。

三个并存的现实

现实含义
上下文是稀缺资源32k 窗口里每一千 token 都宝贵，粗暴的 RAG 式全文注入反而稀释注意力
智能是异构的用户的环境里同时存在高智力云模型（Kimi-K3 级）、低成本高速模型（minimax 级）、本地小模型（qwen3-4B 级）——它们的价格/能力差一个数量级
记忆必须属于用户按产品原则，记忆落在本地文件，不上传、不外发、不绑定任何账号体系
核心洞察

小上下文模型的短板不在「智力」，在「记忆跨度」。如果记忆的收集、整理、提纯可以下沉给低成本模型在后台完成，主模型只需要在正确的时间收到一页摘要——32k 的窗口就足够装下大项目的全貌。

02方案：三个角色，三个点目录，一扇门

2.1 角色剧

主模型 · 编排者

如 Kimi-K3（高智力云模型）

主导对话与编排。它的上下文默认是干净的——不背历史包袱，不被检索噪音稀释。

只在 ANI 敲门时，收到一张不超过 800 token 的记忆便签。

ANI · 门房 / 中断器

如 minimax-m2.7-highspeed（低成本高速）

Autonomous Notice IntERRUPT —— 自主感知中断。daemon 心跳节拍上的分诊代理，类比 MS-DOS 时代的 int 1ch。

扫一眼增量，做三选一分诊：静默 / 唤起整理 / 向主模型递便签。单次调用上下文极小，成本可忽略。

KARPATHY · 书记员

如本地 ollama qwen3-4B（零成本）

专职文档处理：把 ./.raw 里的素材切片编译进 ./.wiki 主题页，维护摘要与互链，接受 lint 体检。

写得不好没关系——失败廉价，下轮重写，lint 兜底。

2.2 数据驻地：三个隐藏点目录

项目根/ ├── ./.raw ← 对话切片，append-only，只进不出（原料仓） ├── ./.wiki ← KARPATHY 编译产物，主题页四件套（成品仓） ├── ./.outputs ← 报告/导出等待交付物（暂存仓） └── .gitignore ← 若已存在，幂等追加三行；不存在则不创建
  • 点目录是系统级工作区，遵循 .git / .vscode / .claude 的通行约定，对用户项目零视觉污染；
  • 默认不进版本控制：检测到 git 仓库且 .gitignore 已存在时，以注释段幂等追加；不擅自创建 .gitignore，不在非 git 目录做任何版本控制假设；
  • 与用户亲手经营的 ./wiki（非隐藏，karpathy-wiki-new 所建）刻意分离：那是用户刻意的知识资产，进 git；这是系统的工作记忆，不进 git。两套并存，互不合并。

2.3 那扇门：ANI 门控注入

本方案与传统「每轮检索 top-k 注入」的分水岭在于：主模型的上下文默认不受打扰。心跳节拍里产生的任何内容，只在 ANI 判定「与当前任务直接相关」时，才在下一个用户输入边界注入主上下文；其余一切静默。

为什么门控优于常开检索

常开 RAG 每轮都往上下文塞 top-k，32k 窗口被持续稀释，且注入噪音是单向累积的。ANI 门控把「要不要打扰主模型」本身变成一个由低成本模型做的显式决策——过滤器的价格是 minimax 级的，保护的是 Kimi-K3 级的注意力。

03用户体验：看得见的只有一行字

3.1 四幕剧（用户视角）

幕场景用户感知
Ⅰ 开工在项目目录首次启动 alice-code无感。./.raw ./.wiki ./.outputs 静默建立；git 仓库的 .gitignore 被幂等追加三行
Ⅱ 工作正常对话、改代码、做决策无感。有意义的片段（决策、代码块、约定）被规则切片进 ./.raw；想确保某条被记住，手动 /raw 记下这条
Ⅲ 生长daemon 心跳节拍，ANI 分诊，KARPATHY 整理近乎无感。状态栏多一行极轻信息：[wiki 12页 · 2h前]；失败静默，只进 daemon.log 与 OTEL trace
Ⅳ 回响三天后回到项目，问"上次那个方案定的什么"主模型收到 ANI 递来的一张便签（≤800 token，标注 [来自 .wiki 的工作记忆]），直接答出三天前的决策与理由

3.2 用户可控的旋钮

  • /raw 记下这条 —— 手动打点，把当前片段显式切片进 ./.raw（已拍板）
  • 状态栏一行 —— [wiki N页 · 最近ingest时间]，照 TokenBudgetBar 的既有模式渲染（已拍板）
  • settings.jsonc 开关 —— memoryWiki: { enabled, autoCreate, injectMaxTokens }，用户可整个关掉
  • 模型指派 —— ANI / KARPATHY 的 modelPolicy 均可在配置中改写，默认值只是推荐

3.3 静默的边界：静默 ≠ 不可知

反面场景（被本设计排除）

ingest 连续失败三天，用户毫无知觉，直到发现"记忆"停在一周前。纯静默不可接受——所以状态栏那一行是信任装置而非装饰：[wiki 12页 · 3天前 ⚠] 一眼可知知识库已停转。不弹窗、不打断，但可审计（daemon.log + OTEL + /wiki-doctor 手动体检）。

04异构模型经济学

本提案把「记忆维护」这件持续发生的事，定价在接近零的档位上：

环节频率承担模型单次上下文成本量级
切片进 ./.raw每条消息无（规则 + 手动 /raw）—0
ANI 心跳分诊每 tick（脏检查为前置）minimax 高速档增量 diff + 计数，<2k≈0，且 .raw 无变化时零调用
KARPATHY 增量 ingestANI 唤起时本地 qwen3-4B新增素材 + 相关主题页0（本地电力）
记忆便签注入ANI 判定必要时—（写入主上下文）≤800 token占主模型窗口，受硬上限约束
主对话编排每轮Kimi-K3 档干净的任务上下文不为记忆维护多花一分钱

这套定价能成立，是因为每个环节都被指派给了能力恰好够用的模型：切片不需要智能，分诊需要速度，整理需要格式遵从，只有最终与用户的对话才需要高智力。这与既有的 multi_model_routing（按能力层选模型）互补而非冲突——那条是按「任务类型」路由，这条是按「角色身份」钉死。

05设计原则与不做的事

5.1 五条原则

  1. 记忆留在本地。./.wiki 是用户磁盘上的纯文本，不上传、不同步云端、不需要账号。跨端同步若未来要做，走 TeamMemorySync 既有协议，且默认关闭。
  2. 失败必须廉价。KARPATHY 写坏一页，lint 检出，下轮重写；ANI 误判一次注入，用户忽略一张便签。任何单点失败都不累积成灾难。
  3. 静默但可审计。无弹窗、无打断；但 daemon.log 有结构化记录，OTEL 有 span，状态栏有一行，/wiki-doctor 可随时手动体检。
  4. 体验一致。所有下载 alice-code 的人，默认模型指派、目录约定、注入上限完全一致；可改，但改的是自己的配置，不存在分档功能。
  5. 不替代用户的知识库。./.wiki 是工作记忆（系统维护、会过时、可重写）；./wiki 是知识资产（用户经营、进 git、长期演化）。前者喂给模型，后者属于人。

5.2 明确不做

  • ✕ 不做常开 RAG 全文注入（稀释主上下文）
  • ✕ 不在非 git 目录创建 .gitignore，不改动用户的版本控制习惯
  • ✕ 不把 ./.wiki 内容上传任何远端（含"匿名统计"）
  • ✕ 不让 ANI/KARPATHY 拥有写用户工作区文件的权限（它们只能写 ./.raw ./.wiki ./.outputs）
  • ✕ 不做向量数据库/嵌入索引——第一期用四件套摘要 + TF 排序，32k 场景下够了

06里程碑：四个 Phase，各自可验收

Phase内容验收底线
P0 约定层
无 LLM		 点目录规范落地；.gitignore 幂等追加；./.raw append-only 格式 + 水位线文件 任意目录启动 alice-code → 三点目录就位；git 仓库下 .gitignore 追加幂等（重复执行无 diff）；非 git 目录零副作用
P1 收集层 规则切片（代码块/决策句）+ /raw 手动打点；karpathy-wiki-ingest 增加 --target ./.wiki；手动触发跑通 一次 30 轮会话结束 → ./.raw 增加 ≥1 个切片；手动 ingest 后 ./.wiki 出现合格主题页（lint 五项全过）
P2 自动化层 ANI 注册为 AgentProfile（modelPolicy fixed → 高速模型）；挂入 daemon scheduledTasks；脏检查 + 三动作分诊状态机 ./.raw 无变化 → 连续 24h 零 LLM 调用；有变化 → 30 分钟内完成一次增量 ingest；ANI 崩溃不影响主会话
P3 回响层 注入便签机制（下一个用户输入边界消费）；≤800 token 硬上限 + 来源标注；状态栏一行 跨 session 提问三天前决策 → 主模型答出且引用便签来源；无关任务时注入率 < 20%；状态栏显示停转告警
推进纪律

每个 Phase 独立交付、独立验收、可单独回滚。P0/P1 不含任何 LLM 行为变更，可随时合入；P2 引入首个后台 LLM 调用，需 feature flag 门控（memory_wiki，默认开）；P3 是用户价值兑现层，未达注入率验收不得宣布完成。

07风险与对策

风险等级对策
本地 4B 模型写主题页质量不足中模板刚性（四件套固定结构）降低翻车率；lint 五项机器兜底；逃生通道：modelPolicy 从 fixed 调成 tier:balanced 路由到云端中档模型，本地模型退守切片
"有意义的片段"判定失误，.raw 垃圾进垃圾出中P1 只做规则切片 + 手动打点（质量下限可控）；LLM 抽取后置到观察期之后；ingest 侧由 KARPATHY 做二次过滤
ANI 误注入，打扰主模型低便签明确标注来源与"二等公民证据，可质疑可忽略"；注入率纳入 P3 验收（<20%）；用户可一键关
后台代理与主会话并发写冲突低.raw append-only + 水位线：主会话只追加，KARPATHY 只读水位线之前；物理上消除写竞争
本地模型不在线，KARPATHY 长期沉默低状态栏时间戳即告警；/wiki-doctor 一键诊断；静默失败但绝不谎报成功（继承 v3.1.2 诚实降级传统）
点目录与用户既有 ./wiki 混淆低命名隔离（隐藏 vs 非隐藏）+ 文档明示「工作记忆 vs 知识资产」二分；skill 一律需显式 --target

08开放问题（评审时拍板）

  1. ANI 与 7 角色 AgentProfile 的关系：ANI 注册为第 8 个 profile，还是作为既有 oracle（后台伴随分析层）的特化实例？技术概要倾向于后者——oracle 的设计语义（预演、风险提示、伴随分析）与 ANI 同构。
  2. .raw 切片的去重与压缩：同一决策被讨论三次，是否需要在 ingest 时合并而非存三份？（倾向：ingest 侧「改写优于堆叠」自然消解，不在切片侧做复杂判重。）
  3. 多项目并行时的 ANI 调度：daemon 同时服务多个项目目录，ANI 是每项目一个 tick 还是全局轮询？（倾向：每项目独立水位线，全局单 tick 轮询脏目录，成本仍 ≈0。）
  4. 记忆便签的呈现形态：注入主上下文之外，是否同时在 TUI 显示"ANI 递了一张便签"？（倾向：是，一行灰色小字，与状态栏同一克制等级。）
先让记忆留下来，再让记忆变聪明。P0 的三个目录，就是这一切的基石。
